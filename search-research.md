# Why “Believer” can be missing from JioSaavn API search

JioSaavn lists [“Believer” by Imagine Dragons on *Evolve*](https://www.jiosaavn.com/song/believer/Mg0zcxdSYXg) (English, 3:24) and has separate listings for compilation versions, including [*Trending Pop 2021*](https://www.jiosaavn.com/song/believer/Ai4oYz1CAlk). The *Evolve* URL is the useful identity check: a title match alone could be another edition, cover, or unrelated song. A public listing proves the record exists, not that it appears in every search or is playable from every region.

## What the upstream issues establish

- [#105](https://github.com/sumitkolhe/jiosaavn-api/issues/105) is an open report for the exact query, `/api/search/songs?query=Believer`, missing international music. The reply suggests changing the entity type to artist; it does not show that song search was fixed. The [controller](https://github.com/sumitkolhe/jiosaavn-api/blob/fc6bd132193d1fc71c2ab3db373e78b92884f67c/src/modules/search/controllers/search.controller.ts#L69-L99) actually uses `Believer` as its song-search example.
- [#23](https://github.com/sumitkolhe/jiosaavn-api/issues/23) is the strongest historical deployment evidence: the owner advised selecting Mumbai for the Vercel function, and the reporter said it worked. [#109](https://github.com/sumitkolhe/jiosaavn-api/issues/109) reports the same website/API mismatch for the Chainsmokers’ “Closer”; a community reply claims the opposite region direction. That reply is not a maintainer finding or a reliable current recommendation. JioSaavn’s own [streaming help](https://help.jiosaavn.com/hc/en-us/articles/360020253792-Do-you-have-English-and-International-music) and [music-rights policy](https://www.jiosaavn.com/corporate/music-rights) explicitly say English/international music is licensed for streaming within India. They do not document exactly how search filters by region.
- [#174](https://github.com/sumitkolhe/jiosaavn-api/issues/174) reports Hindi matches instead of Ed Sheeran’s “Photograph” and raises language selection. JioSaavn [documents a website Music Languages preference](https://help.jiosaavn.com/hc/en-us/articles/360020521471-How-do-I-select-or-change-my-music-languages), but does not document its effect on these upstream calls. [#127](https://github.com/sumitkolhe/jiosaavn-api/issues/127) and [#170](https://github.com/sumitkolhe/jiosaavn-api/issues/170) record related reports, not a verified fix.
- [#130](https://github.com/sumitkolhe/jiosaavn-api/issues/130#issuecomment-2726479131) uses the exact same `Believer` URL but reports an HTML-as-JSON error, not valid JSON with the original missing. The maintainer attributed that specific incident on the old public host to a daily quota; it is not evidence of a catalog problem or proof that all similar parse errors are quota-related.

## What the code establishes

Source inspected: `sumitkolhe/jiosaavn-api` at [`fc6bd13`](https://github.com/sumitkolhe/jiosaavn-api/tree/fc6bd132193d1fc71c2ab3db373e78b92884f67c). The checkout here points to `ODSkyler/jiosaavn-api`, so its `/api/songs?q=...` is not the same route as Sumit’s `/api/songs`.

- Sumit’s `/api/search/songs` forwards `query`, `page`, `limit` as `q`, `p`, `n` to `search.getResults`; defaults are page `0`, limit `10`. The use case maps the upstream results without re-ranking or filtering by language and slices to the requested limit. Neither it nor the controller forwards a language or region option. The shared fetch helper uses `https://www.jiosaavn.com/api.php`, API version `4`, default `ctx=web6dot0`, a random User-Agent, and no browser cookies. [Controller](https://github.com/sumitkolhe/jiosaavn-api/blob/fc6bd132193d1fc71c2ab3db373e78b92884f67c/src/modules/search/controllers/search.controller.ts#L69-L126) · [Use case](https://github.com/sumitkolhe/jiosaavn-api/blob/fc6bd132193d1fc71c2ab3db373e78b92884f67c/src/modules/search/use-cases/search-songs/search-songs.use-case.ts#L17-L30) · [Endpoint constants](https://github.com/sumitkolhe/jiosaavn-api/blob/fc6bd132193d1fc71c2ab3db373e78b92884f67c/src/common/constants/endpoint.constant.ts#L1-L11) · [Fetch helper](https://github.com/sumitkolhe/jiosaavn-api/blob/fc6bd132193d1fc71c2ab3db373e78b92884f67c/src/common/helpers/fetch.helper.ts#L17-L36).
- Sumit’s `/api/search` instead calls `autocomplete.get` and maps the song section it receives. Its results should not be treated as another page of `/api/search/songs`. The separate `/api/songs?link=...` route extracts the song token from a permalink and calls `webapi.get` with `type=song`, so it can distinguish a search miss from a detail lookup miss without assuming playback is available. [Autocomplete use case](https://github.com/sumitkolhe/jiosaavn-api/blob/fc6bd132193d1fc71c2ab3db373e78b92884f67c/src/modules/search/use-cases/search-all/search-all.use-case.ts#L9-L18) · [Song controller](https://github.com/sumitkolhe/jiosaavn-api/blob/fc6bd132193d1fc71c2ab3db373e78b92884f67c/src/modules/songs/controllers/song.controller.ts#L21-L80) · [Link lookup](https://github.com/sumitkolhe/jiosaavn-api/blob/fc6bd132193d1fc71c2ab3db373e78b92884f67c/src/modules/songs/use-cases/get-song-by-link/get-song-by-link.use-case.ts#L12-L20).
- This checkout’s [song search handler](api/songs.js#L152-L229) calls the same `search.getResults` and defaults to `p=1`, `n=20`. Changing `ctx=wap6dot0` to `ctx=web` returned the original first in a direct upstream request, but not from the Cloudflare deployment. Removing the hardcoded English/Mumbai cookie did not fix Cloudflare search either. The [`bom1`](api/songs.js#L1-L3) export is Vercel configuration and does not control Worker egress.

## What remains unverified

The experiments did not isolate the reason for the Cloudflare catalog difference. The deployed `/api/songs?link=...` lookup did return the exact *Evolve* recording by Imagine Dragons; this verifies metadata, not playback or text search.
